  3. Update your “aesd-char-driver” implementation in your assignment 3 and later repository to add the following features:

    1. Add custom seek support to your driver using the llseek file_operations function.  Your seek implementation should:

      1. Support all positional types (SEEK_SET, SEEK_CUR, and SEEK_END) and update the file position accordingly.

        1. For instance, if your driver is storing writes of 5, 7, and 9 bytes each, an file position of 0-5 would represent a byte within the first write, a file position of 6-13 would represent a byte within the second write, and a file position of 14 through 23 would a byte within represent the 3rd write.

    For instance: Consider the content in the table below as handled by your driver, where each string ends with a newline character. An offset of 15 would set the pointer to the second byte of the word “Singapore”, byte "i"

    Grass

    Sentosa

    Singapore

  4. Add ioctl command support for AESDCHAR_IOCSEEKTO as defined in aesd_ioctl.h which is passed a  buffer from user space containing two 4 byte values. Use unlocked_ioctl to implement your ioctl command

    1. The first value represents the command to seek into, based on a zero referenced number of commands currently stored by the driver in the command circular buffer. The command reference is relative to the number of commands currently stored in your circular buffer. You will need to translate into the appropriate offset within your circular buffer based on the current location of the output index.

      1. For instance, in the example above a value of 0 refers to the command “Grass\n”

    2. The second value represents the zero referenced offset within this command to seek into.  All offsets are specified relative to the start of the request.

      1. For instance, if the offset was 2 in the command “Grass”, the seek location should be the letter “a”

    3. The two parameters above will seek to the appropriate place and update the file pointer as described in the seek support details within the previous step.

    4. If the two parameters are out of range of the number of write commands/command length, the ioctl cmd should return -EINVAL

  5. Add special handling for socket write commands to your aesdsocket server application

    1. When the string sent over the socket equals AESDCHAR_IOCSEEKTO:X,Y where X and Y are unsigned decimal integer values, the X should be considered the write command to seek into and the Y should be considered the offset within the write command.

    2. These values should be sent to your driver using the AESDCHAR_IOCSEEKTO ioctl described earlier.  The ioctl command should be performed before any additional writes to your aesdchar device.

    3. Do not write this string command into the aesdchar device as you do with other strings sent to the socket.

    4. Send the content of the aesdchar device back over the socket, as you do with any other string received over the socket interface. We will use this to test the seek command.

    5. Ensure the read of the file and return over the socket uses the same (not closed and re-opened) file descriptor used to send the ioctl, to ensure your file offset is honored for the read command.

Troubleshooting:

1. Attempts to issue ioctl returns "Inappropriate ioctl for device".

  • Ensure your driver is connected to the /dev/aesdchar endpoint through mknod. Ensure you aren't deleting or attempting to create the /dev/aesdchar endpoint within your aesdsocket application.

  • Ensure you've implemented the unlocked_ioctl call in your driver (implementing compat_ioctl is not sufficient).

  • Double check your buildroot submodule and linux kernel version. If you are using a 6.x kernel version through a later buildroot submodule revision than the branch currently recommended for assignments you must define compat_ioctl. Using a definition .compat_ioctl = compat_ptr_ioctl should resolve the issue, or you can move back to the buildroot branch recommended in assignment 5.

2. Attempts to run full-test on qemu fails with rmmod: Can't unload aesdchar resource temporarily unavailable

  • If your test script fails during the driver test step due to failure to unload your driver, please ensure you are not opening the file descriptor for your driver endpoint from aesdsocket until it is accessed.

  • If your sockettest application opens the file descriptor at startup and does not close it, this will prevent the script from successfully testing your driver in isolation by unloading/reloading it. Please modify your aesdsocket application to only open the file descriptor for your /dev/aesdchar device when reading/writing and otherwise close it when not in use or before initial use
