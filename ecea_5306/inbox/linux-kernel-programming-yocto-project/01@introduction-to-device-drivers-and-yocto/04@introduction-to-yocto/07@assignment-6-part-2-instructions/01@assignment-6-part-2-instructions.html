Yocto Installation

  1. Install essential build packages on your build host as described in the “Build Host Packages” section of the yocto quick start guide.

  2. Add yocto poky as a git submodule in the root of your project repository.

    1. Use https://git.yoctoproject.org/poky as the source (see the clone reference at https://git.yoctoproject.org/poky/)

    2. Be sure to git add from the root of your project repository and git commit to save the appropriate commit hash for the buildroot directory before running ./build.sh

    3. Use the branch kirkstone

  3. Update the recipe “aesd-assignments” in the meta-aesd/recipes-aesd folder of your project as discussed in class. This recipe should build your assignment 6 aesdsocket source using the git repository with appropriate commit specified via SRCREV and install associated files in the rootfs of the system.

    1. Remember to add your start script as well using the instructions discussed in lecture videos.

  4. Add your package to core-image-aesd as described in lecture videos.

  5. Use the build.sh script to build your combined image

  6. Use the runqemu.sh script in the root folder which:

    1. Runs source oe-init-build-env from the poky directory to setup your yocto build environment.

    2. Uses runqemu nographic plus appropriate arguments to start QEMU with host port 9000 forwarded to your QEMU instance using slirp.

  7. If not already present, add ssh support to your image using CORE_IMAGE_EXTRA_INSTALL += " openssh" in your core-image-aesd.bb file.

  8. Verify your socket is started automatically when starting qemu on the target. Verify your socket test scripts used for part 1 of your assignment work as expected when running against the qemu target, as they did with the assignment 5 buildroot implementation.

    1. The `./full-test.sh` script in your yocto repository should now complete successfully.  Ensure you have installed sshpass with `sudo apt-get update && sudo apt-get install -y sshpass` as this is required for the test script.

  9. Tag the assignment with “assignment-<assignment number>-complete” once the final commit is pushed onto the respective repositories. The instructions to add a tag can be found here

Validation:

  1. You should be able to clone your final yocto assignment repository to a new directory, run ./build.sh to build the system image and ./runqemu.sh to start the image.

  2. When the QEMU image is started, it should pass port 9000 from the host into the guest image, the aesdsocket utility should be running in daemon mode, and all functionality should match the implementation section.

Troubleshooting:

  1. You see an error about content mismatch on timestamp comparisons, with "Binary Files Differ" included in the output.

    1. This means the logic we have here to remove timestamps from the output file is failing, because the socket output file is being treated as a binary file instead of a text file (external link; opens in a new tab). The reason the output file is treated as a binary file is typically because there are non-printable ASCII characters in the file. There may be non printable ASCII characters in the file for a variety of reason but the most common is probably exceeding array bounds on strings which are missing null termination characters. Look at the output file with a hex editor, find where the binary content is included, and fix your code to ensure you aren't writing anything other than the ASCII string content sent over the socket into your socket file.

  2. Use the cleanall task in bitbake (documentation here (external link; opens in a new tab)) to recover from failures of recipe builds. This will help you clean build a specific recipe. Use this method when a recipe fails for reasons which aren't easy to understand. For instance, sometimes recipes fail to build if your build machine crashed when building due to out of disk space or out of memory conditions. Search the error log for the recipe name (usually in the format recipename_x.x where x.x is the version.

    1. The cleanall task in BitBake is responsible for cleaning up the build artifacts and temporary files associated with a recipe.

    2. When you run bitbake -c cleanall <recipe> it triggers the clean process for the specified recipe.

  3. Logs for troubleshooting: In case of debugging inside qemu, find the logs at "/var/log/messages"

Note: The following links are external and will open in a new tab. Reducing Disk Usage:

If you find yourself out of disk space when building your yocto image, and are unable to free space by deleting content from previous assignments, here are some strategies you can try:

  1. Delete the build/tmp directory to clear out old build content. The shared state cache will allow you to rebuild this content quickly.

  2. Add INHERIT += "rm_work" in your build.conf as referenced here, either by manually editing the build/conf/local.conf file or editing the build script to add this to the file.

    1. Note that this means some files which are potentially useful for troubleshooting builds are missing, especially your local rootfs content in the build/tmp/work directory. Use RM_WORK_EXCLUDE for specific recipes, if needed for troubleshooting, as described here. Adding the image recipe, core-image-aesd, to your RM_WORK_EXCLUDE will mean your work directory contains rootfs content.
