Feature Branch Workflow and also introduce
what's called GitFlow. The Git feature
branch workflow is just a way that you can use Git such that all your feature development would take place on a
dedicated branch. You would use the master
branch, not for development, but just for tracking every time a specific
feature is completed. The nice thing about this
implementation is that you can have multiple
developers that are working on specific
or different features without disturbing
that main codebase. You can have these developers working on same feature
branch, for instance, and sharing that feature branch, but not breaking anything that's working in
the master branch. A key concept here is that the master branch
is never broken. You don't actually
merge in any changes to your development branches until you complete and tested
with that change, and you've had some level
of verification that you aren't going to break anything that's already working
in the master branch. The feature will end with a pull request or
a merge request from the feature branch, and the pull or merge request is a great opportunity to
put in code reviews. Other people on the
team who maybe weren't as involved with development can review the work that you
did and ask questions or ask for changes
based on what they see. An example of how you'd use Git for feature branch workflow. You'd start by checking
out the master. You would pull origin master, you'd make sure you are in sync with the origin master branch. Then you can do git checkout -b for your feature branch name. That feature branch
name is often something like issue-25 or so. For instance, if you're
using GitHub issue tracking, or it could be something
like feature/foo, where foo describes the
name of the feature, or maybe it's fix-foo
if you're fixing a bug. My personal preference of these, is something like issue-25. The reason is if you use some words to describe
your feature or your fix, it might not be obvious to other people what
exactly you're fixing. Whereas if you link back to
an issue tracking database, you can put all the detail
that you want about that and you can
update that easily to include additional
description about what you're
changing or implementing. But your development
team will have its own guidelines about how to do this and you should follow whatever your team is
suggesting to use. But you'll ultimately
check out a branch, do all your commits
on that branch. Then when you're
ready to share with others or when you're
ready to do a code review, you would do git push origin with your feature branch name. At that point, you'll
be ready to do a code review on
the feature branch. This would typically
be assigned to some other person on the team
that would add comments, questions, or suggestions based on the code that you
put in the branch. It will go back to
the developer then to respond to those questions, make new changes based on
the pull request comments. At that point, you can merge the feature into
the master branch. Once you've verified

another git workflow that's based on feature branch that you might hear
about is called GitFlow. GitFlow again is based on the basic Git feature
